# Blocking correction 1 — Narrative must reject unsupported claims everywhere

Current defect:

A narrative can be accepted while an `unsupported` claim appears inside a narrative section, as long as it is omitted from the top-level general `claim_refs`.

This violates the core invariant:

> unsupported candidate claims may exist, but must not silently enter accepted narrative.

## Required behavior

For every narrative record that reaches an accepted/reviewed state:

1. inspect ALL claim references used by the narrative;
2. include:

   * top-level claim refs;
   * claim refs nested in sections;
   * any other schema-supported narrative claim reference location;
3. require every referenced claim to satisfy the allowed support/review state;
4. reject any accepted narrative containing an unsupported claim.

The validator must not depend on a later `delivery` check to catch this.

Narrative acceptance itself is a contractual state and must be valid independently.

## Important positive case

Climate must remain valid because:

`claim_direct_suitability`

exists as an unsupported candidate but is explicitly excluded from accepted narrative.

That pattern must continue to work.

## Required tests

Add at minimum:

### Negative

Accepted narrative:

* top-level `claim_refs` contains only supported claims;
* one nested section references an unsupported claim.

Expected:

* invalid;
* deterministic finding identifying the narrative and offending claim.

### Positive

Unsupported candidate exists in the bundle but is referenced by no accepted narrative content.

Expected:

* valid.

### Positive

All top-level and section-level claim references are supported/allowed.

Expected:

* valid.

Do not special-case climate.

Implement this generically from the schema.

# Blocking correction 2 — ACCEPT WITH EDIT must preserve a complete predecessor

Current defect:

`previous_ref` currently passes validation when the predecessor contains only identifying fields.

That does not preserve the actual prior reviewed content.

## Required behavior

For an `ACCEPT WITH EDIT` lineage:

1. `previous_ref` must resolve;
2. the predecessor must be a complete valid record under the applicable schema/version;
3. predecessor identity must be compatible with the current object:

   * same logical object identity;
   * earlier revision;
4. the predecessor must preserve the prior substantive content, not merely identifiers;
5. where review provenance applies, the predecessor must preserve its review state/provenance;
6. the current revision must preserve a valid lineage to that predecessor.

Do NOT require byte identity between old and edited revision.

The point is preservation of history, not immutability of the edited object.

## Do not over-constrain

Do not require every predecessor to have been accepted if the contract allows editing from another legitimate review state.

Use the existing review semantics.

Do not invent a new review system.

## Required tests

### Negative

`previous_ref` resolves to a record containing only:

* id,
* type,
* revision,
* version identifiers.

Expected:

* invalid.

### Negative

Complete predecessor but:

* incompatible logical identity,
  or
* non-earlier revision.

Expected:

* invalid.

### Positive

Complete valid predecessor with:

* compatible identity;
* earlier revision;
* substantive content;
* preserved review provenance where applicable.

Expected:

* valid.

### Positive compatibility case

Dengue's historical edited review lineage must still validate without migration or rewriting.

# Blocking correction 3 — Prospective execution must bind to complete frozen registration criteria

Current defect:

The prospective registration currently protects question, plan and contract identities, but declared criteria can be modified while the frozen hashes and execution remain unchanged.

This violates the prospective-ordering invariant.

## Required behavior

Execution must reference an immutable/local identity representing the COMPLETE prospective registration used to authorize execution.

That identity must cover, directly or through a deterministic canonical representation:

* question;
* analysis plan;
* authorities/contracts;
* selected inputs;
* input hashes/identities;
* analytical expectations/criteria;
* gate criteria/state needed to authorize execution;
* registration timestamp or its declared registration metadata.

The execution record must reference that frozen registration identity.

If any covered prospective criterion changes after registration, validation must fail unless:

* a new registration revision is created;
* the new execution explicitly references that new revision;
* chronology remains valid.

## Important scope boundary

This is local repository integrity.

Do NOT add:

* external timestamping;
* cryptographic signing infrastructure;
* trusted third-party attestation;
* remote services.

The system must only prove:

> this execution references this preserved registration state in the repository.

It must NOT claim externally certified preregistration.

## Design preference

Prefer the smallest model that closes the gap.

Good options may include:

* a canonical registration hash/digest;
* a frozen registration object referenced by execution;
* a deterministic manifest identity.

Do not duplicate all registration content into execution if a stable identity reference is sufficient.

Explain the chosen design.

## Required tests

### Negative

Start from a valid native/prospective study.

After registration but without updating execution reference:

* change a criterion or analytical expectation.

Expected:

* validation fails.

### Negative

Change gate criteria after execution identity was fixed.

Expected:

* validation fails.

### Positive

Create a new registration revision with new criteria and a new execution that references it, preserving valid chronology.

Expected:

* valid.

### Positive compatibility

Climate historical bundle remains unchanged and valid.

The transient v0.2 interpretation may use the new mechanism only if it does not fabricate historical approval or alter pilot history.
