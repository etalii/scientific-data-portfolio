# Download Log Contract

## Contract identity

- **Contract ID:** `download_log`
- **Version:** `1.0.0`
- **Artifact:** `data/metadata/download_log.csv`
- **Producer:** `scripts/acquisition/01_download_data.R`
- **Primary consumer:** `scripts/validation/02_validate_downloads.R`

## Purpose

`download_log.csv` is an append-only operational event log for download runs.
It records execution-level and resource-level outcomes without modifying raw
data. It is not versioned in Git; the versioned resources catalog and a future
provenance manifest provide the durable acquisition record.

## Invariants

- Every `01_download_data.R` execution emits a run event when the log is
  writable.
- Existing log rows are never changed or removed.
- Only one `01_download_data.R` execution may be active in a workspace.
- Every resource-level row refers to a resource from the input catalog.
- `destination_path` is always relative to the project root and is never an
  absolute system path.
- A successful resource outcome records a non-empty SHA-256 checksum and a
  positive file size.

## Exclusive execution lock

The shared lock path is configured in `artifacts.acquisition_validation_lock`
and must be inside the configured metadata directory. It is a Git-ignored
operational directory, not scientific metadata or data.

The acquisition and validation scripts acquire it with one `dir.create()`
operation. If that operation does not create the directory because it already
exists, the acquiring script aborts before observing or changing raw-data state
and associated metadata. The lock covers the entire execution.

The directory may contain only diagnostic information such as `run_id`, UTC
acquisition timestamp, PID and hostname. Those values are never used to infer
that a lock is stale. Controlled termination releases the lock through cleanup
handlers. A residual lock is never removed automatically; a future execution
aborts with its location and requires human inspection.

## Schema

| Column | Type | Nullable | Description |
| --- | --- | --- | --- |
| `log_schema_version` | string | No | Constant `1.0.0`. |
| `event_type` | string | No | Controlled event vocabulary. |
| `run_id` | string | No | Opaque identifier shared by all events from one execution. |
| `event_at_utc` | ISO 8601 UTC string | No | Timestamp generated by the project. |
| `catalog_contract_version` | string | No | Input resources catalog contract version. |
| `resource_id` | string | Yes | Required for `resource_result`; empty for run events. |
| `download_url` | string | Yes | Source URL for a resource event. |
| `local_filename` | string | Yes | Catalog filename for a resource event. |
| `destination_path` | project-relative path | Yes | Raw-data destination for a resource event. |
| `outcome` | string | No | Controlled outcome vocabulary. |
| `attempt_count` | integer | Yes | Number of network attempts for a resource event. |
| `http_status` | integer | Yes | Final HTTP response status when available. |
| `file_size_bytes` | integer | Yes | Final file size for successful resource outcomes. |
| `sha256` | lowercase hexadecimal string | Yes | SHA-256 for successful or verified existing files. |
| `error_class` | string | Yes | Stable category for a failure outcome. |
| `error_message` | string | Yes | Human-readable diagnostic; must not contain credentials. |

## Controlled vocabularies

`event_type` values:

- `run_started`
- `run_failed_preflight`
- `resource_result`
- `run_finished`

`outcome` values:

- `started`
- `failed_preflight`
- `downloaded`
- `skipped_existing_verified`
- `failed_download`
- `failed_integrity`
- `conflict_existing_file`
- `completed`
- `completed_with_failures`

For `run_started`, `run_failed_preflight` and `run_finished`, resource-level
fields are empty. For `resource_result`, `resource_id`, `download_url`,
`local_filename`, `destination_path` and `attempt_count` are required.

`event_at_utc` uses the exact UTC representation
`YYYY-MM-DDTHH:MM:SSZ`. `attempt_count` is a non-negative integer;
`http_status`, when present, is an integer from 100 through 599.
`destination_path` must be project-relative. The log represents null values as
empty CSV fields.

`error_class` values are controlled for failures:

- `connection_or_timeout`
- `tls_certificate_validation`
- `http_error`
- `empty_download`
- `existing_file`
- `publication_copy`
- `publication_verification`
- `publication_rename`
- `unexpected_error`
- `preflight`

For `resource_result`, `downloaded` requires a positive `attempt_count`, a 2xx
`http_status`, a positive `file_size_bytes` and a lowercase 64-character
SHA-256. `skipped_existing_verified` requires `attempt_count = 0`, no HTTP
status, and the same size and checksum fields. Both successful outcomes leave
`error_class` and `error_message` empty. All failed resource outcomes require
non-empty `error_class` and `error_message` and leave size and checksum empty.
Run-event outcomes are constrained to `started` for `run_started`,
`failed_preflight` for `run_failed_preflight`, and `completed` or
`completed_with_failures` for `run_finished`. `run_started` and `run_finished`
leave error fields empty; `run_failed_preflight` requires both error fields.

## Retry policy

Retry behavior is controlled only by `download.timeout_seconds`,
`download.max_retries` and `download.retry_backoff_seconds` in
`config/project.yml`.

Retries are allowed only for reasonably transient failures: connection and
timeout errors, HTTP 429, and appropriate HTTP 5xx responses. TLS certificate
validation failures are recorded as `tls_certificate_validation` and are never
retried: repeating the same request cannot establish trust in an invalid or
untrusted certificate chain. HTTP 4xx errors other than 429, malformed
responses, integrity failures and local filesystem errors are not retried.

`download.max_retries` is the maximum number of attempts after the initial
request. The delay before retry number *n* is
`download.retry_backoff_seconds * 2^(n - 1)`.

## Logical append-only log and atomic physical update

The log has logical append-only semantics: no historical event is modified,
reordered or removed. To provide crash-safe publication, it uses a different
physical mechanism for each new event:

1. Validate the existing CSV syntax, schema, column order, schema version and
   controlled vocabularies.
2. Create a temporary file in the same directory as `download_log.csv`.
3. Copy the existing validated log bytes unchanged to that temporary file and
   append exactly one serialized event row.
4. Atomically rename the temporary file over `download_log.csv`.

Creating the temporary in the log directory keeps the final rename in the same
filesystem. Copying historical bytes rather than reserializing parsed rows
preserves their exact order and content. If the existing log is invalid, the
script aborts before downloads or raw-data changes.

## Raw-data policy

Downloads are written to the configured staging directory, which must be
outside `data/raw/` and ignored by Git. A file is eligible for publication only
after a successful response, a non-empty size check and SHA-256 calculation.

The final filename defined by `local_filename` is published only after all
required checks complete. When staging and raw data are on different
filesystems, publication uses this sequence:

```text
external staging
→ hidden publication temporary in data/raw/
→ size and SHA-256 verification
→ atomic rename to local_filename
```

The publication temporary uses this exact project-owned convention:

```text
.argentina_dengue_publish--{resource_id}--{run_id}.part
```

Both identifiers must be validated filesystem-safe strings. The fixed hidden
prefix and `.part` suffix ensure that a temporary cannot equal a catalog
`local_filename`. Publication temporaries are implementation artifacts, not
raw datasets; validation, processing, merging and every other downstream stage
must ignore them.

Managed failures remove the publication temporary. At the start of a future
run, any file matching exactly the project-owned temporary convention is treated
as evidence of an interrupted prior publication. The script records a
`run_failed_preflight` event and aborts without deleting it. Files that do not
match the convention are never considered temporary artifacts and are never
deleted automatically.

External staging files are unique to a run and are never reused by a later run.
Controlled failures remove them. Residual external staging files do not enter
the raw-data set and require manual housekeeping if an interrupted run leaves
them behind.

Raw files are immutable. An existing destination is reused only when it can be
verified against a compatible successful log record; otherwise it is logged as
`conflict_existing_file` and never overwritten.

## Validation handoff

`02_validate_downloads.R` must validate the resources with terminal outcomes
`downloaded` or `skipped_existing_verified`. It uses the catalog, the log and
the raw file; it must not discover files by scanning `data/raw/` alone.
